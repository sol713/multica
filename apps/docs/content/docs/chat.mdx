Chat fits work that hasn't formed a clear issue yet: sorting out ideas, checking on the workspace, discussing an approach, or having an agent finish a small task first.

**Chat is a one-to-one conversation between you and an [agent](/agents)** — stepping outside the [issue](/issues) board. The agent starts with **no issue context** — it isn't looking at your board and won't turn the conversation into issues on its own — and the entire conversation is **fully private** (nobody else in the [workspace](/workspaces), including admins, can see it). It fits discussing an approach with an agent, brainstorming, or asking a question that does not belong to any issue.

A chat is **not bound to any issue**: the agent doesn't automatically receive an issue's description and comments, but it can still use the Multica CLI to query workspaces, projects, issues, and skills within its permissions.

A chat can also carry background. Click **+** at the bottom left of the input and choose **Project context** to attach a [project](/projects) to the conversation; when the agent runs, it receives that project's description, repositories, and other resources.

## Start a conversation

1. Open **Chat** in the sidebar.
2. Click new and pick an agent you have permission to run.
3. Type a message; you can also attach images or files.
4. After you send, Multica creates a run for the message, and the reply comes back to the current conversation.

If the runtime is offline, the message waits until it comes back online. Once the agent is archived, or you lose permission to run it, you can't send new messages.

Before the first message, Chat shows up to three suggestions configured for the selected agent. Selecting one copies its full prompt into the composer without sending it, so you can adapt it first. Agents without configured suggestions use localized general-purpose examples.

## Chat vs. issues

| Need | Better fit |
|---|---|
| Quick questions, exploring an approach, or private drafts | **Chat** |
| A clear assignee, status, priority, and deliverable | **Issue** |
| Letting teammates see the background and continue the discussion | **Issue** |
| A quick look at workspace information with no work record needed | **Chat** |

Direct chats created in Multica are visible only to their creator; other workspace members and admins cannot read them. Conclusions the team needs to see together should be written into an issue, a project description, or a skill.

## Multi-turn context

A conversation tries to continue the original session in the AI coding tool, so later messages don't need to repeat earlier content. Multica stores the session ID and routes subsequent runs to a runtime that can access that session.

If the local session no longer exists, the context can't be continued, or the previous error shouldn't be reused, the runtime starts from a fresh session. The conversation's message history is kept either way.

## Watch and stop a run

While the agent runs, the UI shows the current phase and tool activity. Expand **View details** to inspect the run in full.

To interrupt, click the stop button next to the input. Content already returned to the conversation is kept; input not yet processed is restored to the editor when possible.

## Organize the conversation list

Conversations can be renamed, pinned, archived, and deleted:

- **Pin** keeps frequently used conversations at the top of the list;
- **Archive** moves a conversation to Archived and makes it read-only;
- **Unarchive** lets you send messages again;
- **Delete** permanently removes the conversation and its messages.

If a conversation is bound to an external channel (such as Slack), archiving breaks the binding; unarchiving does not restore it — bind again.

<Callout type="warning">
Deleting a conversation cannot be undone and stops any runs in it that haven't finished. Archive instead when you just don't need it for now.
</Callout>

## Shared browser (optional)

Open **Browser** in a conversation header to watch the agent's Octop Browser viewport. The browser runs on the daemon's machine, so it can reach that machine's localhost pages. Web and desktop share this panel; compact screens open it in a dialog.

Install Python 3.12+ and Chrome/Chromium on the daemon machine, then create a dedicated environment:

```bash
python3.12 -m venv ~/.multica/browser-venv
~/.multica/browser-venv/bin/python -m pip install octop-browser==1.0.0
export MULTICA_BROWSER_PYTHON="$HOME/.multica/browser-venv/bin/python"
export MULTICA_BROWSER_ENABLED=1
multica daemon
```

Windows users can create the environment with `py -3.12 -m venv "$HOME/.multica/browser-venv"`, install with its `Scripts/python.exe`, and set the two environment variables before restarting the daemon. If Chrome is not auto-detected, set `BROWSER_USE_CHROME_BIN` to its executable.

Send a message first to bind the chat to a runtime. Browser tools are injected into **new turns** for Claude, Codex, DSH, Hermes, Qoder, MCode and OpenCode runtimes that support HTTP MCP. Ask the agent to use `multica-browser` rather than a separately configured browser tool. An agent already running when this feature is enabled needs a new turn.

**Take control** waits for any current browser action to finish, then prevents further shared-browser tool calls by the agent. Click the viewport, use the address bar or paste text using the input below the viewport. **Return to agent** lets it continue in the same browser. Hiding the panel does not return control or stop the browser; **Stop browser** closes Chrome while retaining its profile.

Profiles and login state stay under `~/.multica/browser-profiles`, isolated by workspace and chat. Screenshots and input pass through Multica's authenticated daemon connection, not a public CDP endpoint. At most eight browser sessions remain open per daemon; sessions without activity are closed after 15 minutes. A disconnected daemon shows an error, not a live viewport. Existing agent tools, terminal commands and third-party browser integrations are not sandboxed by this control toggle; it governs the shared `multica-browser` tool only. Browser viewport updates are polled while the panel is open (up to 2 fps); this initial version supports click, text, keyboard, scrolling and tabs, not file upload, drag-and-drop, audio or video streaming.
